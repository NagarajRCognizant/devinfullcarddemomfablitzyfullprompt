# CardDemo Account Management + User Administration + Credit Card Authorizations — COBOL/CICS/VSAM/IMS/DB2/MQ → Java

**This is a local functional-equivalence build, not a production-ready deployment.** Production
deployment, cloud integration, production identity (external IdP, MFA, revocation), encryption,
secrets management, infrastructure security, scalability, high availability, disaster recovery and
production operations are outside the current scope.

The COBOL sources under `app/` are unmodified. Everything generated by the conversion lives in this
directory.

## 1. What was converted

Three capabilities, converted into three bounded contexts behind one gateway.

### Account Management

| Source | Was | Became |
|---|---|---|
| `COACTVWC` + `COACTVW.bms` (transaction `CAVW`) | CICS Account View enquiry | `AccountViewService` + `GET /api/accounts/{id}` + `AccountViewScreen.tsx` |
| `COACTUPC` + `COACTUP.bms` (transaction `CAUP`) | CICS Account Update | `AccountUpdateService`/`AccountUpdateValidator` + `fetch`/`validate`/`confirm` operations + `AccountUpdateScreen.tsx` |
| `CBACT01C` under `READACCT.jcl` | batch extract of the ACCT KSDS | Spring Batch `readAcctJob` producing the same 107-byte FB, 110-byte FB and 84-byte VB extracts |
| `CSUTLDTC` (+ `CSUTLDPY`) | LE date validation service | `DateValidationService` + `DateEditor` |
| `COMEN01C` access rules | menu option gating by operator type | `MenuAccessService` + `GET /api/menu`, gated by the operator type in the sign-on token |
| `ACCTFILE.jcl`, `CUSTFILE.jcl`, `XREFFILE.jcl` (IDCAMS) | VSAM define/REPRO | account-service Flyway `V1__create_account_management_schema.sql` + `V2__load_sample_data.sql` |
| ACCT / CUSTOMER / CARDXREF KSDS + the account alternate index | VSAM | `account`, `customer`, `card_xref`, `ix_card_xref_acct_id` |

### User Administration and sign-on

| Source | Was | Became |
|---|---|---|
| `COSGN00C` + `COSGN00.bms` (transaction `CC00`) | CICS sign-on, routing by operator type | Keycloak realm `carddemo` asks for the password and a one-time code, the SPA obtains an RS256 token with Authorization Code + PKCE, `GET /api/me` reads the USRSEC row and routes by its type + `SignOnScreen.tsx` (`docs/25-authentication-and-mfa-architecture.md`) |
| `COADM01C` + `COADM01.bms` (transaction `CA00`) | CICS administrator menu | `AdminMenuService` + `GET /api/admin-menu` + `AdminMenuScreen.tsx` |
| `COUSR00C` + `COUSR00.bms` | user list, ten rows a page, PF7/PF8 browsing | `UserListService` + `GET /api/users` + `UserListScreen.tsx` |
| `COUSR01C` / `COUSR02C` / `COUSR03C` + their maps | add / update / delete a user | `UserAdminService` + `POST`/`PUT`/`DELETE /api/users` + `UserAddScreen`/`UserUpdateScreen`/`UserDeleteScreen` |
| `CSUSR01Y` (8/20/20/8/1 record) | USRSEC record layout | `SecurityUserEntity` / table `security_user`, fixed widths kept as `CHAR` |
| `DUSRSECJ.jcl` (IDCAMS) + `AWS.M2.CARDDEMO.USRSEC.PS` | USRSEC KSDS define/REPRO and its ten records | identity-service Flyway `V1__create_identity_schema.sql` + `V2__load_usrsec_data.sql` |

The operator type the source carried in the COMMAREA is now a realm role in the token Keycloak
signs, so no caller can assert its own type.

### Credit Card Authorizations

| Source | Was | Became |
|---|---|---|
| `COPAUA0C` (transaction `CP00`, MQ-triggered) | authorization request processor reading `AWS.M2.CARDDEMO.PAUTH.REQUEST` and replying to `MQMD-REPLYTOQ` under `MQMD-CORRELID` | `AuthorizationRequestListener` + `AuthorizationRequestProcessor` + `AuthorizationReplyPublisher` over Kafka topics `carddemo.authorization.request.v1` / `…reply.v1`, card number as the partition key |
| `COPAUS0C` + `COPAU00.bms` (transaction `CPVS`) | authorization summary, five rows a page, PF7/PF8 browsing, `S` selection | `AuthorizationInquiryService.summary` + `GET /api/authorizations` + `AuthorizationSummaryScreen.tsx` |
| `COPAUS1C` + `COPAU01.bms` (transaction `CPVD`) | authorization detail, PF3/PF5/PF8 | `AuthorizationInquiryService.detail` + `GET /api/authorizations/{accountId}/{authKey}` + `AuthorizationDetailScreen.tsx` |
| `COPAUS2C` (DB2, `CPVDTRAN`/`DB201PLN`) | fraud marking and un-marking | `FraudMarkingService` + `POST /api/authorizations/{accountId}/{authKey}/fraud` |
| `CBPAUP0C` under `CBPAUP0J` | BMP purge of expired authorizations with IMS checkpointing | Spring Batch `purgeExpiredAuthorizationsJob` in `batch-auth-purge`, chunk-committed and restartable |
| `PAUDBLOD` / `PAUDBUNL` / `DBUNLDGS` + `LOADPADB.jcl` | IMS load and unload utilities | `tools/ims_authorization_unload.py` + `tools/generate_authorization_seed_sql.py` + Flyway `V2__load_authorization_sample_data.sql` |
| IMS HIDAM `DBPAUTP0` (`PAUTSUM0` root, `PAUTDTL1` child), index `DBPAUTX0` | IMS DB | `pending_auth_summary` / `pending_auth_detail` parent-child model; the HIDAM primary index is the primary-key b-tree |
| DB2 `AUTHFRDS` + index `XAUTHFRD` | fraud table | `auth_fraud` in the authorization-owned database |
| MQ queues and the `MQTM` CICS trigger | queue-triggered work distribution | Kafka consumer group, bounded retry with backoff, `…request.DLT`, request log for duplicate detection and a transactional reply outbox (`docs/23-messaging-modernization-mapping.md`) |

The authorization service owns `carddemo_authorization` and never reads the `carddemo` or
`carddemo_identity` databases: the cardholder data `COPAUA0C` read from the account files is fetched
over the account service's `GET /api/cardholders/{cardNumber}` boundary.

## 6. Prerequisites and commands

JDK 21, Maven 3.9+, Node 20+, PostgreSQL 16, and Docker — the default authentication mode needs the
Keycloak realm, which Compose runs.

```bash
# databases — one pair per service, plus the test databases the integration tests use
for db in carddemo carddemo_test carddemo_identity carddemo_identity_test \
          carddemo_authorization carddemo_authorization_test; do
  psql -U carddemo -h 127.0.0.1 -d postgres -c "CREATE DATABASE $db"; done

# build + all tests + coverage gates
cd modernization && JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64 mvn clean verify

# the realm, the databases and every service, which is the supported way to run the default
# authentication mode: sign-on needs Keycloak, and Keycloak needs its own database
cp .env.example .env   # then fill in the realm and client secrets it asks for
docker compose up -d --build

# or, without Compose, the jars against a Keycloak of your own
# (Flyway creates each schema and loads its seed data on first start)
export KEYCLOAK_ISSUER_URI=http://127.0.0.1:8088/realms/carddemo KEYCLOAK_URL=http://127.0.0.1:8088
java -jar identity-service/target/carddemo-identity-service.jar &   # 127.0.0.1:8081
java -jar account-service/target/carddemo-account-service.jar &     # 127.0.0.1:8080
java -jar authorization-service/target/carddemo-authorization-service.jar &  # 127.0.0.1:8082
java -jar gateway/target/carddemo-gateway.jar &                     # 127.0.0.1:8090

# signing on is a browser flow — password, then a one-time code, then the screens; a shell cannot
# obtain a token, because the realm's browser client grants no password flow. Without a token:
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8090/api/users   # 401

# the browser end-to-end suite drives both factors, enrolment, refusals and the journeys
cd e2e && npm install && npx playwright install chromium && npm run test

# the shell smoke run needs the one-factor legacy mode, which exists for parity evidence only
# (docs/15-local-execution-guide.md)
tools/smoke.sh http://127.0.0.1:8090

# UI
cd frontend && npm ci && npm run dev                                # 127.0.0.1:5173

# authorization summary and detail through the gateway
curl -sS -H "Authorization: Bearer ${TOKEN}" 'http://127.0.0.1:8090/api/authorizations?accountId=48'

# converted CBPAUP0J purge job (expiry days, checkpoint frequency and debug come from the SYSIN
# card equivalents in application.yml or --carddemo.batch.authpurge.* overrides)
java -jar batch-auth-purge/target/carddemo-batch-auth-purge.jar \
  --spring.batch.job.enabled=true --spring.batch.job.name=purgeExpiredAuthorizationsJob

# authorization data migration: decode the supplied EBCDIC IMS unload, regenerate the seed
# migration, then reconcile the loaded rows against the decoded segments
python3 tools/generate_authorization_seed_sql.py ..
python3 tools/reconcile_authorization_data.py ..

# converted READACCT batch job
java -jar batch-account-extract/target/carddemo-batch-account-extract.jar \
  --spring.batch.job.name=readAcctJob \
  --carddemo.batch.readacct.output-directory=./target/readacct run.id=1

# reset a database and reload its seed data (the IDCAMS define/REPRO equivalent)
psql -U carddemo -h 127.0.0.1 -d postgres \
  -c "DROP DATABASE carddemo" -c "CREATE DATABASE carddemo"   # then restart that service
```

Seeded operators: `ADMIN001`–`ADMIN005` (administrators) and `USER0001`–`USER0005` (regular users),
all with password `PASSWORD` — the ten records the supplied USRSEC file holds. Every credential here
is a throwaway local value.

Ports: gateway 8090, account service 8080, identity service 8081, authorization service 8082, UI
5173, PostgreSQL 5432 (5433–5435 under Compose), Kafka 9092 under Compose, all bound to 127.0.0.1.
Troubleshooting: `docs/15-local-execution-guide.md` §12.

## 8. Assumptions and exclusions

- The ASCII sample data is treated as authoritative where it disagrees with the EBCDIC copy (UCR-01).
- Authorisation is the source's single operator-type flag, carried as a realm role in the RS256 token
  Keycloak signs: the user screens require an administrator, the two account transactions are open to
  both types per the `COMEN01C` option table. There are no finer scopes (L-10).
- The USRSEC password column is still clear text, because `CSUSR01Y` is and the administration screens
  write it (UCR-14), but the default mode never compares it: the password Keycloak verifies is the
  realm's, hashed by Keycloak. Only `carddemo.security.mode=legacy` compares the USRSEC column, and it
  exists for the `COSGN00C` parity evidence and as the rollback path
  (`docs/28-authentication-security-controls.md`).
- An unknown user is still reported differently from a wrong password by the legacy sign-on, because
  the source does both (UCR-14). The realm's own pages are Keycloak's, and they do say which factor was
  refused - "Invalid username or password", then "Invalid authenticator code"; what is factor-neutral is
  the message the SPA shows after a refused or abandoned sign-on, which is all the application itself
  ever learns (`docs/27-mfa-enrolment-and-signon-flow.md` §3).
- Terminal transport — PF keys, COMMAREA, `SEND`/`RECEIVE MAP`, attribute bytes, cursor mechanics — is
  deliberately not reproduced; its business intent is preserved through the API and UI.
- `DFHAID` and `DFHBMSCA` are IBM platform plumbing and are not reimplemented.
- Capabilities outside account management, user administration and authorizations (cards,
  transactions, reporting, bill payment) are inventoried and dispositioned but not converted.
- Authorization requests are accepted from Kafka rather than MQ, and the reply is published from a
  transactional outbox after the authorization commits rather than before it, so the source's
  at-most-once delivery becomes at-least-once with idempotent replay (CMD-10 to CMD-15).
- Two source behaviours in the authorization closure were corrected because source evidence
  corroborates the correct behaviour, and both are recorded as deliberate deltas: the purge now
  persists the available-credit adjustment it computed (UCR-27), and the declined-total accumulation
  no longer adds the previous authorization's amount (UCR-30).
- One supplied unload record carries a blank account key and is reported rather than seeded with an
  invented key (UCR-31); two summary character fields arrive as LOW-VALUES and are stored as blanks
  (UCR-32).
- Sign-on is performed by a Keycloak realm over OIDC with TOTP as the second factor, run locally in
  Compose in development mode over HTTP on the loopback interface; no cloud service, running
  Kubernetes cluster, KMS or production certificate is present, and a real deployment has to terminate
  TLS in front of the realm (`docs/29-keycloak-deployment-and-operations.md`). No real customer data
  and no realm or client secret is committed.

## 9. Known limitations and REVIEW REQUIRED items

Full detail in `docs/17-limitations-and-review-required.md`; the registers behind them are
`docs/11-unsupported-construct-register.md` and `docs/12-consistency-model-delta-register.md`.

Headlines:

- The Helm chart and the CI workflow are static-validated only; the Compose stack, Keycloak included,
  is verified running.
- Integration tests use a local PostgreSQL database and, for the realm, the Compose Keycloak driven by
  Playwright rather than Testcontainers (Docker Engine API too old here) — L-22.
- Access tokens are valid for their 15-minute lifespan and are not introspected per call, so a role
  change takes effect at the next token; the SPA renews silently and sign-off ends the realm session.
- `COBDATFT` is missing from the repository and was reconstructed from its copybook and its caller.
- Hard-coded batch amounts, the FICO range and the earliest-year bound need business sign-off.
- Source defects preserved deliberately and flagged: stale account fields after a failed read, the
  date-of-birth offsets in the concurrency check, the commented-out address-line-2 validation, the
  unchecked read before a user delete and the `Unable to Update User...` wording after a failed
  delete. No AS-IS defect was corrected in the account and user closures; two were corrected in the
  authorization closure (UCR-27, UCR-30), each with source evidence and a proving test.
- No accessibility audit and no dependency-vulnerability scan were performed. Browser-driven
  validation exists for the authentication and the two journeys (`e2e/`), not for every screen.
- No performance or load test was run: no production message volumes, MQ statistics or batch
  schedule are present in the repository, so the Kafka partition count, listener concurrency and
  chunk size are documented defaults to be tuned before go-live
  (`docs/19-test-strategy-and-quality-gates.md` §6).
- The authorization consumer was proven against an embedded Kafka broker, not a multi-broker
  cluster, so replication and rebalance behaviour under broker loss is untested here.
- The batch job restarts from the last committed chunk when relaunched with unchanged parameters,
  unlike the source's all-or-nothing data-set rewrite.

## 10. Could not be automated

Helm deployment to a cluster; a CI workflow run; Testcontainers-provisioned databases and realm;
accessibility auditing; a production-mode Keycloak behind TLS; dependency vulnerability scanning; any
comparison against real mainframe output; and confirmation of the intended behaviour behind the
REVIEW REQUIRED items.
